# 작업 팀

사용자의 작업 방식을 일곱 모드로 나눠 가진 Claude 하위 에이전트 팀이다. 정의는 `.claude/agents/vow-*.md`에 있다. 저장소마다 다른 값은 [TEAM-REPO.md](TEAM-REPO.md)에 있다('여러 저장소'). 저장소 규칙([AGENTS.md](../AGENTS.md))이 이 문서보다 우선한다. Codex는 이 팀을 쓰지 않고 AGENTS.md만 따른다.

| 팀원 | 모드 | 맡는 일 | 파일 수정 |
|---|---|---|---|
| `vow-design` | 설계 | 요청 → 실제 목적, 명세, 사용자가 정할 것 | 안 함 |
| `vow-fact` | 사실 | 법·제도·통계·가격 조사, 출처·기준일 표 | 안 함 |
| `vow-build` | 제작 | 유일한 작성자. 브랜치 → 구현 → 시험 → push → PR | 함 |
| `vow-diagnose` | 진단 | 시험·CI 실패와 리뷰 지적의 원인, 최소 수정안 | 안 함 |
| `vow-judge` | 판단 | PR 전 반대 검토, 최종 화면 확인, 결정 목록 압축 | 안 함 |
| `vow-respond` | 대응 | 열린 PR 점검·나눔, 다음 팀원 정하기, GitHub 기록(라벨·판정 댓글·의견 해결 처리·main 받아오기) | 안 함 |
| `vow-accept` | 수락 | 자동 병합 조건을 다시 확인하고 통과한 PR 하나를 병합 | 안 함 |
| 사용자 | — | 자동 병합 조건 밖의 병합, 외부로 나가는 행위 승인, 결과가 갈리는 결정 | — |

## 사용자에 대해 (관찰)

근거는 사용자 작업 규칙(Vowline CHAT v3), marry-me의 AGENTS.md·README·CHANGELOG와 PR #1~#5다.

- 규칙과 시험으로 맡긴다. 약속보다 자동 검사를 믿는다. AGENTS.md의 절대 규칙 대부분이 시험으로 검사된다.
- 보고는 결과 → 검증 → 가정 → 남은 문제로 받는다.
- 결정권은 직접 쥔다: 아티팩트 반영, 결과가 갈리는 결정, 자동 병합 조건 밖의 병합. 조건을 통과한 PR의 병합은 팀에 맡긴다(2026-10-28).
- 요구는 써 보면서 구체화된다. marry-me PR #5에서 두 번 바뀌었다('가격 비교 탭에는 참고 시세만' → 직접 금액 입력, '지역에 맞는 값 하나 고르기' → 모두 펼쳐 보이기).
- 휴대폰 기준으로 만든다: 폭 320~430px, 라이트·다크, 누르는 영역 44px, 대비 4.5:1.
- GPT(Codex)와 Claude를 함께 쓰고, Codex가 PR을 리뷰한다.
- 병합 대기가 쌓인다. 팀이 PR을 늘리기만 하면 대기열이 길어진다. 저장소마다의 대기 현황은 TEAM-REPO.md '진행 상황'에 있다.
- GitHub 작업은 말하지 않아도 팀이 역할을 나눠 하길 원한다. 개발 용어(CI, 리뷰 봇, P2)를 풀지 않은 보고는 무엇을 하겠다는 건지 알기 어려워한다(2026-10-28, marry-me PR #6 보고).

## 공통 규칙 (모든 팀원)

1. 요청의 문자가 아닌 실제 목적을 따른다. 안전한 가정으로 진행하고, 결과가 갈릴 때만 묻는다.
2. 결론을 지탱하는 주장 한둘을 집중해서 확인한다. 확인한 것과 추정을 섞지 않는다.
3. 자료끼리 어긋나면 어긋난 지점과 채택 근거를 밝힌다.
4. 정확도가 더 오르지 않는 지점에서 멈춘다.
5. 범위 밖 결함은 고치지 않고 '남은 문제'에 적는다.
6. 되돌릴 수 없거나 외부로 나가는 행위(main 반영, 배포, 아티팩트 반영, 다른 저장소·서비스에 쓰기)는 사용자 승인 전에 하지 않는다. 예외: vow-accept가 '자동 병합 조건'을 모두 통과한 PR을 병합하는 것. 이 조건이 든 PR(TEAM-REPO.md '팀 도입 PR')을 사용자가 병합한 것을 승인으로 본다.
7. 보고는 결과 → 검증 → 가정 → 남은 문제. 서두·중계·요약·형식적 면책 없이. 코드블록·표에 있는 내용을 산문으로 반복하지 않는다. 메인이 사용자에게 하는 보고는 '사용자에게 보고'를 따른다.

## 팀 규칙

1. 조율은 메인 세션(사용자와 대화하는 Claude)이 한다. 하위 에이전트는 서로를 직접 부르지 못하므로, 팀원은 결과 끝에 `다음:`으로 넘길 팀원을 적고 메인이 부른다.
2. 파일을 고치고 push하는 것은 `vow-build`만, GitHub 기록(라벨, 댓글, 의견 해결 처리, main 받아오기)은 `vow-respond`만, 병합은 `vow-accept`만 한다. 메인 세션을 포함한 나머지는 읽기와 시험 실행만 한다. 같은 파일을 둘이 동시에 고치지 않는다(README '한 번에 한 AI만 고치세요').
3. 같은 파일을 고치는 PR이 이미 열려 있으면 새 PR을 열기 전에 사용자에게 그 PR의 병합·종료를 먼저 묻는다. 이어 가라고 하면 그 브랜치 위에 쌓고 PR '가정'에 적는다.
4. 사용자에게는 결정만 올린다. PR마다 '사용자가 정할 것'은 3개 이하. 팀이 안전하게 정할 수 있는 것은 정하고 '가정'에 적는다.
5. 같은 진단으로 두 번 막히거나 같은 검토 지적으로 두 번 돌아오면 멈추고 사용자에게 보고한다.
6. 팀원은 모두 같은 모델이라 맹점을 공유한다. `vow-judge`는 Codex 리뷰를 대신하지 않는다. Codex 지적은 `vow-diagnose`가 실제 경로를 따져 확인한다.
7. 사실 내용(TEAM-REPO.md '사실 내용')은 `vow-fact`의 출처·기준일 표 없이 바꾸지 않는다.

## 언제 팀으로 하나

Claude Code에서 이 저장소의 GitHub 작업은 사용자가 '팀으로'라고 하지 않아도 항상 팀으로 한다. GitHub 작업이란 파일을 바꾸는 일, 브랜치·커밋·push·PR을 만드는 일, 열린 PR의 시험 실패나 Codex 검토 의견을 처리하는 일이다. 파일도 GitHub도 바꾸지 않는 일(질문에 답하기, PR 상태 알려 주기)은 메인이 직접 답한다.

| 팀원 | 거치는 때 | 건너뛰는 때 |
|---|---|---|
| vow-design | 결과가 여러 갈래로 갈릴 수 있는 요청: 새 기능, 구조·저장 형식 변경, 기존 기능 제거, 새 규칙 | 한 곳만 바뀌고 결과가 하나로 정해지는 요청(오타, 문구 한 줄, 원인이 정해진 수정) |
| vow-fact | 사실 내용(TEAM-REPO.md '사실 내용')을 바꾸거나 넣을 때 | 그 밖 |
| vow-build | 파일을 바꾸는 모든 작업 | — |
| vow-diagnose | 시험 실패, GitHub 자동 시험 실패, 화면 깨짐, Codex 검토 의견 | 실패·의견이 없을 때 |
| vow-judge | vow-build가 바꾼 것이 있으면 매번, 사용자에게 보고하기 전에. 고침이 한 줄이어도, 검토 의견을 반영한 뒤에도 | — (화면이 안 바뀌면 화면 확인만 '해당 없음') |
| vow-respond | 예약 점검마다, 사용자가 열린 PR 점검을 시킬 때 | 그 밖 |
| vow-accept | vow-respond가 병합 후보를 골랐을 때 | 후보가 없을 때 |

가장 작은 GitHub 작업도 vow-build와 vow-judge는 거친다.

## 흐름

```
요청
 ├─ vow-design  명세            ← 건너뛸 때: '언제 팀으로 하나'
 └─ vow-fact    사실 표          ← 사실이 걸릴 때만, design과 동시에
        ▼
 사용자: '사용자가 정할 것'에 답   ← 없으면 건너뜀
        ▼
 vow-build      브랜치·구현·시험·push
        │ 시험·CI 실패 → vow-diagnose → vow-build
        ▼
 vow-judge      통과 / 수정 필요 → vow-build (같은 지적 2회면 멈춤)
        ▼ 통과
 PR             vow-build 본문 + vow-judge의 '사용자가 정할 것'
        │ Codex 지적 → vow-diagnose → vow-build → vow-judge
        ▼
 사용자 병합 (자동 병합 조건을 통과하면 예약 점검의 vow-accept, '대응팀')
```

## 부르는 법

- Claude Code: 따로 부르지 않아도 된다. GitHub 작업이면 메인이 '언제 팀으로 하나'와 '흐름'대로 진행한다. 한 명만 쓰려면 "vow-judge로 PR #5 검토해 줘"처럼 이름을 댄다.
- 이름으로 부르지 못할 때(세션이 시작된 뒤 에이전트 파일이 생겼거나, 그 파일이 없는 브랜치에서 세션을 시작했을 때): 메인이 일반 하위 에이전트에게 "`.claude/agents/vow-○○.md`를 먼저 읽고 그 지침대로 그 역할만 하라"고 맡긴다. 파일은 지금 브랜치 → `origin/main`(`git show origin/main:.claude/agents/vow-○○.md`) → '예약 점검' 1의 브랜치 순서로, 처음 있는 곳에서 읽게 한다. 이때는 머리말의 `tools` 제한이 걸리지 않는다. 그래서 `vow-build`가 아닌 팀원에게는 지시에 "파일을 고치지 않는다, Bash는 읽기만"을 그대로 적는다. 단 `vow-respond`에는 "파일을 고치지 않는다. GitHub에 쓰는 것은 라벨·댓글·의견 해결 처리·main 받아오기만, push·병합은 하지 않는다"를, `vow-accept`에는 "파일을 고치지 않는다. GitHub에 쓰는 것은 확인한 head를 못 박은 병합 한 번만"을 적는다.
- claude.ai: 프로젝트 하나에 팀원 하나. 에이전트 파일에서 `---` 아래 본문과 이 문서의 '공통 규칙'을 프로젝트 지침에 붙인다. 파일 수정과 시험 실행이 필요한 `vow-build`는 Claude Code에서 쓴다.

## 사용자에게 보고

메인이 사용자에게 하는 보고(작업이 끝났을 때, 또는 물어야 해서 멈출 때)는 이 형식을 따른다. PR 본문은 AGENTS.md 작업 흐름 5를 따른다.

1. 결과: 첫 줄에 무엇이 바뀌었는지 한 문장으로 쓴다. 이어서 팀원 표를 쓰고, 부른 팀원 줄을 모두 채운다(대화 작업은 최소 다섯 줄, 예약 점검은 일곱 줄).

   | 팀원 | 한 일 |
   |---|---|
   | 설계(vow-design) | 명세: 바꿀 곳 3개, 정할 것 없음 |
   | 사실(vow-fact) | 건너뜀: 사실 내용과 무관 |
   | 제작(vow-build) | 문서 3개 고침, marry-me PR #6(작업 팀 만들기)에 올림 |
   | 진단(vow-diagnose) | 건너뜀: 실패 없음 |
   | 판단(vow-judge) | 한 번 고쳐 달라고 한 뒤 통과 |

   건너뛴 팀원은 '건너뜀: 이유', 아직 차례가 오지 않은 팀원은 '아직'이라고 쓴다. 이름으로 부르지 못해 다른 방법으로 맡겼으면 '가정'에 적는다.
2. 검증 → 가정 → 남은 문제(공통 규칙 7).
3. 정할 것: 맨 끝에 3개 이하로 쓴다. 없으면 '정할 것: 없음'.

### 쉬운 말

사용자가 읽는 글(대화 보고, PR 본문, PR 댓글)에는 개발 용어 대신 쉬운 말을 쓴다. GitHub 화면에서 찾아야 하는 이름이면 괄호에 붙인다. 예: "GitHub 자동 시험(CI) 통과". 표에 없는 용어도 같은 방식으로 푼다. PR 번호에는 무엇의 PR인지 붙인다. 예: "marry-me PR #6(작업 팀 만들기)".

| 용어 | 쓸 말 |
|---|---|
| CI, 체크, Actions | GitHub 자동 시험 |
| 리뷰 봇, Codex 리뷰 | Codex(GPT)가 PR에 자동으로 다는 검토 의견 |
| P0~P3 | Codex가 매긴 중요도. 숫자가 작을수록 급함 |
| flake, 불안정 | 같은 코드인데 돌릴 때마다 결과가 바뀌는 시험 |
| push | GitHub에 올리기 |
| 배포, Pages | 공개 웹주소에 새 버전 올리기 |
| main | 공개 웹주소에 올라가는 원본 |
| 병합 | PR의 바뀐 부분을 원본에 합치기 |
| diff | 바뀐 부분 |
| 충돌(conflict) | 두 PR이 같은 곳을 고쳐 GitHub가 자동으로 합치지 못함 |
| 하위 에이전트 | 팀원 |
| head 커밋, SHA | PR의 마지막 커밋 번호(앞 7자리) |
| update-branch, 뒤처짐 | main의 새 내용을 PR에 받아오기 |

### 끝의 질문

- 질문 하나에 행동 하나만 묻는다. '예'라고 하면 누가 무엇을 하고 무엇은 하지 않는지 쓴다.
- '처리할까요', '진행할까요', '지켜볼까요'만으로 묻지 않는다.
- 고를 것이 둘 이상이면 번호를 달고, 팀이 권하는 쪽과 이유를 한 줄로 쓴다.

나쁨: marry-me PR #6의 CI와 리뷰를 지켜보다가 처리할까요?

좋음: marry-me PR #6(작업 팀 만들기)에서 GitHub 자동 시험이 실패하거나 Codex 검토 의견이 달리면, 진단(vow-diagnose)이 원인을 찾고 제작(vow-build)이 같은 PR에 고쳐 올릴까요? 병합은 하지 않습니다.

## 대응팀

`vow-respond`(대응)와 `vow-accept`(수락)는 열린 PR을 정해진 시간에 점검하고, 조건을 통과한 PR을 사용자 대신 병합한다. 고치는 일은 vow-diagnose → vow-build → vow-judge가 한다. main에 병합하면 일어나는 일은 TEAM-REPO.md '배포'에 있다.

### 예약 점검

메인이 등록한 예약 작업이 매일 09:48·19:48(한국 시간)에 새 세션을 연다. 그 세션의 메인은 이 순서로 진행한다.

1. 규칙(AGENTS.md, 이 문서, TEAM-REPO.md, `.claude/agents/`)을 `origin/main`에서 읽는다. origin/main에 이 절이 없으면 예약 작업 지시문이 알려 준 브랜치에서 읽고 점검과 고침만 한다(병합 없음).
2. vow-respond가 점검하고, 나누고, 기록한다(main 받아오기, 라벨).
3. '고칠 것'은 vow-diagnose → vow-build(그 PR 브랜치에 커밋을 더함, 강제 push 없음) → vow-judge 순서로 처리한다. '판정 필요'는 vow-judge에 넘긴다. main 시험이 실패 중이면 PR의 시험 실패는 진단하지 않고 '기다림'으로 둔다.
4. vow-respond가 판정 댓글을 남기고, 고친 의견을 해결 처리하고, '사용자 결정' 라벨을 단다.
5. 병합 후보가 있으면 vow-accept가 하나를 병합한다.
6. '사용자에게 보고' 형식(일곱 줄)으로 보고한다. main 시험 실패나 병합이 있으면 결과 첫 줄에 쓴다.

예약 점검은 새 PR을 열지 않는다. 같은 PR에 '수정 필요' 판정이 두 번 쌓이면 더 고치지 않고 사용자 결정으로 올린다(팀 규칙 5).

### 자동 병합 조건

origin/main에 있는 이 목록과 이 목록이 가리키는 TEAM-REPO.md 절만 유효하다. 모두 맞아야 병합한다.

1. 작성자가 저장소 소유자 계정(TEAM-REPO.md '저장소')이고, head가 이 저장소의 브랜치이며(포크 아님), 초안이 아니고, base가 main이고, TEAM-REPO.md '팀 도입 PR'이 병합된 뒤에 열렸다(PR의 `created_at`이 팀 도입 PR의 `merged_at`보다 뒤). 그 전에 열린 PR은 사용자가 병합한다.
2. 바뀐 파일이 모두 TEAM-REPO.md '자동 병합 저장소 조건' 2의 허용 파일 안에 있다. 그 밖의 파일이 바뀌면 사용자가 병합한다.
3. TEAM-REPO.md '자동 병합 저장소 조건' 3의 구간이 main과 글자 그대로 같다. 구간 표시가 main에 없으면 실패로 본다. 또 새 사실 내용(TEAM-REPO.md '사실 내용'에 해당)을 더하거나 바꾸지 않았다(조건 8의 '통과' 판정에 '새 사실 내용: 없음'). 더하거나 바꿨으면 사용자가 병합한다.
4. 시험 파일(TEAM-REPO.md '시험 파일')에서 지운 줄에 `test(`·`expect(`가 없고, 더한 줄에 `.skip`·`.fixme`·`.only`가 없다.
5. main 최신 커밋의 GitHub 자동 시험에서 `test`가 성공이다. 결과가 없으면 실패로 본다.
6. head가 main 최신 커밋을 포함하고(뒤처지지 않음) 충돌이 없다.
7. head 커밋의 GitHub 자동 시험에서 `test`가 성공이고, 나머지는 성공이거나 건너뜀이다.
8. 같은 head 커밋에 저장소 소유자 계정이 단 '통과' 판정 댓글이 있고, 그 뒤 소유자 계정이 같은 커밋에 단 '수정 필요' 판정이 없다. 다른 사람이 단 판정 댓글은 없는 것으로 본다.
9. chatgpt-codex-connector[bot]이 단 Codex 검토 요약 댓글에서 코드 검토(Code Review) 상태가 완료(Completed)이고, 해결 안 된 리뷰 스레드가 0개다.
10. '사용자 결정' 라벨이 없다.

병합은 merge commit으로, 확인한 head 커밋을 못 박아서, 한 번 점검에 하나만 한다. 브랜치는 지우지 않는다.

### 판정 댓글

```
<!-- vow-judge sha=<head 커밋 40자> verdict=pass|fix -->
판단(vow-judge): 통과 | 수정 필요 — 커밋 <앞 7자>
<판정 본문>
```

'사용자 결정' 댓글은 첫 줄을 `<!-- vow-respond decision sha=<40자> -->`로 쓰고, 이유와 사용자가 할 일(직접 병합, 또는 질문에 답하고 라벨 지우기)을 적는다. 라벨은 사용자만 지운다.

### 병합 뒤

다음 점검에서 main의 시험과 배포를 확인한다. 실패하면 되돌리지 않는다. 조건 5 때문에 자동 병합은 저절로 멈춘다. 보고 첫 줄과 병합한 PR 댓글로 알리고, vow-diagnose가 찾은 원인과 고칠 방법을 적는다. 되돌릴지 고칠지는 사용자가 정한다.

## 여러 저장소

이 팀은 여러 저장소에서 같은 공통 파일로 일한다.

- 원본은 `dudwlstjr3-maker/marry-me`의 main이다. 공통 파일 8개(`.claude/agents/vow-*.md` 7개와 이 문서)는 모든 저장소에서 글자 그대로 같고, 원본에서만 고친다. 다른 저장소의 vow-build는 공통 파일을 원본 main에서 그대로 복사하는 PR만 연다.
- 저장소마다 다른 것은 `docs/TEAM-REPO.md`, AGENTS.md 작업 흐름 3의 예외 문장, CLAUDE.md의 Claude Code 줄이다. 공통 파일은 저장소 이름·소유자·파일 이름을 직접 쓰지 않고 TEAM-REPO.md의 절을 가리킨다. GitHub 경로는 `repos/{owner}/{repo}/...`로 쓴다(`gh api`가 지금 저장소로 채운다).
- 어긋남 확인: 예약 점검 때 vow-respond가 원본이 아닌 저장소마다 공통 파일 8개의 `sha`(`gh api repos/<저장소>/contents/<파일>?ref=main`)를 원본의 `git rev-parse origin/main:<파일>`과 비교한다. 다르면 보고만 하고, 맞추는 PR을 열지 사용자에게 묻는다(예약 점검은 새 PR을 열지 않는다).
- TEAM-REPO.md에 꼭 있어야 할 절:

  | 절 | 담는 것 |
  |---|---|
  | 저장소 | 저장소 이름, 소유자 계정 |
  | 팀 도입 PR | 공통 파일을 처음 들인 PR. 사용자가 이 PR을 병합한 것이 자동 병합 승인이다(공통 규칙 6, 자동 병합 조건 1) |
  | 배포 | main에 병합하면 일어나는 일 |
  | 시험 파일 | 새 기능의 시험을 더하는 파일(자동 병합 조건 4) |
  | 화면 확인 | 앱을 띄우고 여는 방법, 쓰면 안 되는 명령 |
  | 사실 내용 | 출처·기준일 없이 바꾸지 않는 내용이 있는 곳, 바꿀 때 시험하는 방법 |
  | 추가 확인 | vow-judge 확인 목록에 더할 이 저장소의 항목 |
  | 자동 병합 저장소 조건 | 자동 병합 조건 2의 허용 파일, 3의 구간 |
  | 진행 상황 | 열려 있는 PR과 병합 대기 |

- 새 저장소 들이는 순서:
  1. AGENTS.md나 CLAUDE.md를 만들거나 고치는 열린 PR이 있으면 사용자에게 먼저 묻는다.
  2. vow-build가 원본 main에서 공통 파일 8개를 복사하고, 그 저장소 AGENTS.md '절대 지킬 것'에 맞춰 TEAM-REPO.md를 쓰고, AGENTS.md·CLAUDE.md를 한 줄씩 고친다.
  3. vow-judge가 확인한다: 공통 파일 8개의 `sha`가 원본과 같은지, TEAM-REPO.md에 위 절이 다 있는지, '절대 지킬 것' 하나하나가 자동 병합 조건이나 시험 중 하나에 걸리는지.
  4. 사용자가 병합한다. 이것이 그 저장소의 자동 병합 승인이다.
  5. 메인이 예약 작업에 그 저장소를 더한다.
